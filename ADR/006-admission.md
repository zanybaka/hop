# 006. Ограничить создание резерва и приглашения

Принято для локальной реализации 2026-11-20. Дополняет [ADR 004](004-single-server-short-code.md).

## Контекст и решение

Короткий код уже ограничен по адресу и суммарно. Создание резерва и приглашения в пару занимают общую ёмкость и общие слоты. Сервер проверяет оба предела до того, как принять резерв или выдать приглашение. Сверх предела ответ 429 и заголовок `Retry-After`.

Адрес берётся из TCP-соединения. В режиме локального доверенного прокси сервер слушает только loopback и берёт один IP из `X-Hop-Client-IP`. `X-Forwarded-For` адрес не задаёт. Счётчики не растут вместе с числом адресов.

Отмена резерва и истечение его срока возвращают занятую этим адресом долю. Приглашение держит слот до исходного срока, в том числе после отклонения. Чтение уже сохранённой передачи и вход по уже выданному приглашению этим пределом не закрываются.

## Последствия

Клиент видит отказ на создании и может повторить запрос после `Retry-After`. Общий предел остаётся общим для всех адресов. Числовые значения пределов записаны у оператора, не в этом репозитории.

## Реализация и проверка

`src/admission.mjs` ведёт пределы. `src/server.mjs` применяет их к `POST /api/v1/reservations` и `POST /api/v1/pairing/offers`. Контракты в [API публикации](../docs/publication-api.md) и [протоколе приглашения](../docs/pairing.md).

- [x] Нагрузка одного адреса получает 429 до занятия общей ёмкости, другой адрес завершает передачу.
- [x] Внешний `X-Forwarded-For` не меняет адрес.
- [x] Отмена и таймаут освобождают резерв. Несколько передач с одного адреса проходят в пределах допуска. Ответ содержит `Retry-After`.
- [x] Размер счётчиков ограничен при большом числе адресов.
