# 001. Шифровать содержимое в клиенте перед публикацией

Дата: 2026-11-14. Решение действует для локальной вертикали полной ссылки.

## Контекст

Получатель должен открыть текст и файлы после отключения отправителя. Хранилище получает зашифрованные байты. Подлинный код клиента является исходным допущением. Полная ссылка должна давать получателю доступ без аккаунта.

## Решение

Клиент создаёт случайный ключ AES-256 и шифрует контейнер через Web Crypto AES-GCM. Он хранит ключ в части ссылки после `#` и передаёт хранилищу только отдельный случайный идентификатор и шифротекст. Дополнительные данные AES-GCM связывают запись с этим идентификатором. Формат конверта и ссылки версионирован.

Серверное расшифрование дало бы хранилищу доступ к содержимому. Обмен только между одновременно открытыми клиентами лишил бы получателя доступа после выхода отправителя. Выбранная схема позволяет хранить зашифрованную запись до срока передачи.

## Последствия

Человек с полной ссылкой может читать передачу. Владелец управляет записью по отдельному механизму, который предстоит определить. Подлинность кода страницы, защита ручного кода, отзыв доступа и реальный бюджет памяти остаются отдельными критериями приёмки. Текущий клиент шифрует каждый контейнер целиком в памяти.

## Реализация и проверка

`src/envelope.mjs` задаёт создание ключа, построение и разбор ссылки, шифрование и расшифрование. `src/container.mjs` задаёт формат содержимого. `docs/envelope.md` и `docs/container.md` описывают поля и совместимость. При подключении HTTP клиент передаёт только идентификатор и шифротекст. Получатель разбирает контейнер после проверки тега.

- [x] Новый клиент расшифровывает текст и файл по полной ссылке.
- [x] Неверный ключ, другой идентификатор и подмена шифротекста отклоняются.
- [x] Неизвестная версия отклоняется, пустой контейнер читается.
- [ ] HTTP и браузерные проверки выполняются в HOP-005 и HOP-006.
