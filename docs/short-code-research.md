# Короткий код и получение после отключения отправителя

Исследование для TECHSPEC от 2026-11-14. Производственный протокол не выбран и не проверен. Сценарий владельца сохраняется: отправить данные, записать 6–8 символов, закрыть отправителя, позже получить данные на другом устройстве по этим символам.

## Что установлено

Короткий код не делает отложенный доступ невозможным. Он ограничивает запас секретности, а архитектура определяет, кто и с какой стоимостью может проверять догадки. Нельзя обещать одинаковую защиту от внешнего пользователя, кражи только базы и полного захвата всей серверной системы.

В алфавите из 32 равновероятных символов случайные 6 символов дают 30 бит, 8 символов дают 40 бит. Это расчет пространства вариантов, а не оценка времени взлома. Разделение части кода под открытый идентификатор уменьшает секретную часть. Предлагается исследовать восемь случайных символов; это не утвержденный формат протокола.

| Случай | Что требуется проверить |
|---|---|
| Обычная работа сервиса | Код, ключ и открытое содержимое не должны попадать серверу и в логи |
| Внешний перебор через сервис | Лимиты запросов, глобальный бюджет попыток, защита от распределенного перебора, утечка существования передач и отказ в обслуживании |
| Кража базы без отдельных серверных секретов | Какие именно записи украдены и можно ли по ним проверять догадки без обращения к сервису |
| Полный доступ к серверному коду, данным и секретам | Обычные программные лимиты можно обойти; проверка догадок может стать автономной |
| Подмена веб-клиента | Вне согласованного исходного допущения о подлинном коде страницы; рассматривается отдельно |

## Кандидаты

### Один обычный сервер

Исследовать протокол восстановления клиентского ключа через короткий секрет с защитой от внешнего перебора. OPAQUE является кандидатом для анализа, не готовым решением всей задачи. RFC 9807 описывает скрытие пароля при регистрации и аутентификации, но прямо сохраняет риск перебора после компрометации сервера. Ключевой вывод: выбор PAKE не устраняет ограничения слабого секрета. [RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html)

Для hop отдельно нужно решить поиск передачи без учетной записи. Передавать код как открытый идентификатор и одновременно объявлять его секретом нельзя. Быстрый хеш того же кода в таблице поиска также может стать более дешевой проверкой догадки, чем основной протокол. Нужны проверка полного обмена сообщениями, способ адресации и независимый криптографический разбор. Эти замечания являются анализом применимости к hop, не утверждениями RFC о конкретной реализации hop.

Медленная функция получения ключа, например Argon2id, повышает стоимость перебора, но не добавляет случайности исходному коду. Требуется измерить задержку и память на целевых браузерах и стоимость атак, включая поиск по идентификатору. Пока нет оснований обещать конкретное время взлома или достаточность 40 бит. [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)

### Защищенный контур восстановления

Signal SVR3 демонстрирует восстановление ключей с разделением доверия между разными аппаратно защищенными компонентами и облачными провайдерами. Его гарантии зависят от доверия к этим компонентам; их нельзя переносить на обычный сервер с лимитом запросов. [Работа авторов SVR3, OSDI 2024](https://www.usenix.org/conference/osdi24/presentation/connell)

Применимость к hop пока не доказана. Нужно изучить адресацию без аккаунта, поддержку веб-клиента, проверку подлинности защищенных компонентов, восстановление после сбоев, поддержку и стоимость развертывания. Несколько процессов на одной машине или несколько машин под полным контролем одного злоумышленника сами по себе не дают этой гарантии.

### Распределенное восстановление на независимых серверах

TOPPSS описывает восстановление секрета по паролю при участии порогового числа серверов, без достаточного знания секрета у меньшей коалиции серверов. Это отдельный кандидат для сохранения короткого ручного ввода и получения при закрытом отправителе. [Работа авторов TOPPSS](https://eprint.iacr.org/2017/363)

Для hop можно исследовать вариант с двумя необходимыми независимыми участниками восстановления. Это не готовая интеграция: требуется подобрать проверенную реализацию, решить адресацию без аккаунта, ограничение онлайн-догадок, разделение полномочий, обновления и восстановление после сбоев. При требовании обоих участников недоступность одного мешает получению. Полный захват всех необходимых участников или их сговор снимает это преимущество. Два процесса на той же VPS не создают независимую границу доверия.

Нельзя свести схему к простому разрезанию файла ключа пополам и обещать защиту короткого кода: требуется полный протокол парольного восстановления. Кандидат не выбран владельцем, новые серверы не разрешены.

### Два одновременно доступных устройства

Magic Wormhole использует короткий код для защищенного обмена между двумя участниками. Это полезный ориентир для живого соединения, но не решение исходного сценария с уже закрытым отправителем. Сохранение сообщений в очереди не означает, что рукопожатие может завершиться без дальнейшего участия отправителя. [Документация проекта](https://github.com/magic-wormhole/magic-wormhole/blob/master/docs/api.rst)

## Что не является защитой от полного захвата

- Обычный лимит запросов не ограничивает оператора, который контролирует код проверки и все секреты.
- Истечение ссылки не удаляет копию, которую атакующий уже сохранил.
- Публичный исходный код помогает проверке, но сам по себе не доказывает поведение работающего сервиса.
- Перенос всей секретности в QR или длинную ссылку меняет исходный сценарий и не согласован владельцем.

## Следующее решение

Владелец пока не подтвердил принятие риска перебора после полного захвата сервера. До этого нельзя закрывать T1 или ослаблять требование R5. Для односерверного варианта нужен проверенный полный протокол, включая поиск передачи, затем испытания производительности и анализ атак. Для более сильного варианта нужна оценка защищенного контура. Реализацию криптографии, инфраструктуру и новые зависимости это исследование не разрешает.

## Локальный эксперимент 2026-11-14

Проверен отдельный эксперимент: детерминированная слепая RSA-подпись, раздельное получение адреса и ключа через HKDF, AES-256-GCM. Свежий процесс получателя восстановил текст по восьми символам и публичным настройкам после завершения отправителя. Примитив побайтно прошел внешний вектор Appendix A.4. Клиент не передает открытый код или ключ, адрес не является быстрым хешем кода. Это результат проверки экспериментальной схемы, не принятие производственного протокола. [RFC 9474](https://www.rfc-editor.org/rfc/rfc9474.html)

Офлайн-перебор с базой и серверным секретом восстановил тестовый текст, обходя HTTP-лимит. Такая возможность есть и у самого оператора сервера. Небольшой искусственный список кандидатов не измеряет стойкость случайного восьмисимвольного кода. Копирование базы и получение серверного секрета имеют разные последствия; безопасность первого случая пока не доказана полноценным анализом атак.

Есть дополнительное ограничение кандидата: RFC 9474 §7.3 предупреждает об утечках низкоэнтропийного входа при злонамеренной генерации ключа подписанта. Прототип предполагает честную генерацию; закрепление публичного ключа не доказывает ее. Поэтому успешное восстановление при закрытом отправителе не закрывает требование защиты от недоверенного сервера. Проверка в отдельных локальных процессах также не подтверждает работу браузеров. T1 остается открыт. [RFC 9474, Message Entropy](https://www.rfc-editor.org/rfc/rfc9474.html#section-7.3)

## Эксперимент с двумя сервисами

Клиент восстановил текст после выхода отправителя по восьми символам и общей публичной конфигурации. В эксперименте два сервиса выполняют независимые слепые RSA-подписи. Адрес для поиска и ключ шифрования выводятся из обоих результатов. Тест перебора с копией базы и одним серверным секретом проверил одну догадку запросом ко второму сервису и получил 429 на следующей. При наличии обоих секретов тест восстановил текст офлайн. Два процесса на одной машине моделируют эту границу, а не создают её. Экспериментальная конструкция использует примитив RFC 9474. Гарантии TOPPSS относятся к отдельному протоколу. [RFC 9474](https://www.rfc-editor.org/rfc/rfc9474.html) · [TOPPSS](https://eprint.iacr.org/2017/363)

Лимит опыта исчерпывается для всех получателей сразу и сбрасывается при перезапуске. Сохранённый результат проверки кода работает после остановки сервисов. При неизменных ключах он пригоден против новых записей с тем же кодом. Для дальнейшего выбора протокола нужно проверить, как совместить анонимный поиск, долговечный лимит и смену ключей. T1 остается открыт.

## Проверка смены ключей

Локальная проверка сохранила получение по восьми символам после смены пары ключей. Получатель пробует действующие пары, начиная с текущей. Прежний результат догадки не дал адрес и ключ новой пары для того же кода. Счётчик SQLite сохранился после аварийного завершения и ограничил параллельную выдачу ответов с двух процессов. Счётчик на пару дополняет общий лимит окна, который действует при обращении к любой паре.

Для продукта нужно решить расход попыток на перебор пар, совпадения кодов у живых записей и блокировку честных получателей при исчерпании общего лимита. Истечение пары закрывает доступ через API, но не уничтожает сохранённые результаты догадок. Локальная проверка не подтверждает удаление ключей или независимость сервисов.
