# API публикации v1

Локальный сервис запускается командой `node src/server.mjs STATE_DIRECTORY [PORT]` на loopback. Команда `node --test test/*.test.mjs` проверяет модули клиента и сервера.

С `HOP_BASE_PATH=/hop` все пути ниже получают префикс `/hop`, включая статические ресурсы. Запрос страницы `/hop` перенаправляется на `/hop/`. Внешний прокси сохраняет префикс при передаче запросов. `HOP_PUBLIC_ORIGIN` задаёт внешний HTTP или HTTPS origin для проверки сигнальных запросов. Адрес клиента для лимита коротких кодов берётся из TCP-соединения. Политику проверки адреса за прокси нужно выбрать перед выпуском.

Данные передаются как [зашифрованный конверт](envelope.md). Авторизация записи использует отдельные 32 случайных байта в hex, созданные клиентом. Сервер хранит только SHA-256 этого значения. Его владелец использует для создания и замены. Клиент получателя знает идентификатор и ключ шифрования из полной ссылки. Ключ расшифрования не отправляется. На будущей площадке канал должен работать через HTTPS.

| Запрос | Поля и результат |
| --- | --- |
| POST /api/v1/reservations | Bearer владельца, JSON с `id`, `version`, `bytes` и `hasFiles`. Для создания версия 0, допускаются `protected` и `lifetime` в миллисекундах. Ответ 201 содержит одноразовый `token` и размер. |
| PUT /api/v1/uploads/:token | Тело из зарезервированных байтов конверта и совпадающий Content-Length. Отсутствующий размер даёт 411, несовпадение даёт 413. Ответ 201 содержит `version` и `expiresAt` в миллисекундах Unix. |
| DELETE /api/v1/uploads/:token | Отменяет неиспользованный резерв. |
| GET /api/v1/records/:id | Возвращает шифротекст, версию, срок и при наличии одноразовое подтверждение в заголовках `X-Hop-Version`, `X-Hop-Expires-At`, `X-Hop-Receipt`. |
| POST /api/v1/receipts/:token | Учитывает завершённую выдачу текущей версии. Клиент подтверждает после проверки целостности. Ответ 200 содержит новый `expiresAt`. |

Код 403 означает отсутствие прав записи, 404 означает отсутствующую или истёкшую запись или резерв, 409 означает конфликт версии или повторную операцию, 413 означает превышение размера и 507 означает нехватку места. При отказе старое состояние остается доступным. Подтверждение привязано к выдаче данных и не доказывает, что получатель расшифровал их. Сервер применяет абсолютный предел срока и ограничение места независимо от подтверждения.

Клиент и сервер используют один контракт. При несовместимом изменении добавить версию API и проверку старого клиента. Размер и флаг наличия файлов являются метаданными, видимыми серверу. Он ограничивает размер шифротекста. Клиенты независимо проверяют внутренние пределы контейнера после расшифрования. Интерфейс не должен помещать ссылку, Bearer или ключи в диагностику.

Совместная запись добавляет `GET /api/v1/exchange/:id` с Bearer владельца или участника. Ответ содержит `mode`, `canWrite`, `version` и `expiresAt`. Владелец также получает список идентификаторов и признаков присутствия. `POST /api/v1/exchange/:id/invite` принимает JSON `fingerprint` с SHA-256 разрешения, `POST /api/v1/exchange/:id/mode` принимает `mode` со значением `read` или `exchange`. Оба требуют Bearer владельца. При режиме обмена резерв принимает Bearer участника, а фиксация повторно проверяет разрешение. Обновление старого клиента для действующих ссылок не требуется. Детали хранения и пределы в [контракте прав](participants.md).

`POST /api/v1/exchange/:id/one-use` резервирует место за отпечатком одноразового приглашения, авторизация владельцем. `POST /api/v1/exchange/:id/claim` принимает Bearer приглашения и отпечаток ключа браузера в JSON `fingerprint`. При успехе приглашение расходуется. Старый маршрут `invite` используется для разрешения уже подтверждённой пары. `POST /api/v1/exchange/:id/revoke-write` принимает Bearer владельца и JSON `member`. Он отзывает только запись и возвращает обновлённый список. Эти операции добавлены к существующему API.

Короткий код использует [отдельные маршруты API v1](short-code-api.md). Полная ссылка получает шифротекст по обычному адресу записи.

### Общая ссылка в режимах чтения и обмена

Владелец получает `shareGeneration` через GET настроек и регистрирует отпечаток общего приглашения с помощью `POST /api/v1/exchange/:id/share`. JSON содержит `fingerprint`, текущий `locator` и `generation`. Сервер принимает только Bearer владельца. Повтор той же регистрации безопасен. Неактуальный адрес или поколение возвращают 409.

Новое приглашение из панели подключения содержит `/join/<64 hex>` во фрагменте полной ссылки. QR кодирует ту же ссылку. Обёртка нового короткого кода переносит то же приглашение. Получатель предъявляет его как Bearer в `POST /api/v1/exchange/:locator/claim-shared` и передаёт в JSON `fingerprint` своего ключа браузера и открытый ключ восстановления `key`. Ответ 200 содержит стабильный `id` управления. Приглашение расходует одно из семи мест на каждый браузер. Повтор с тем же ключом возвращает тот же результат. При заполнении списка сервер отвечает 507, и браузер предлагает чтение.

Сервер проверяет сохранённый режим при каждой записи участника. Смена режима не меняет общую ссылку. Форма только для чтения остаётся доступной по старой полной ссылке и старым коротким кодам. Старые личные приглашения обслуживаются маршрутом `claim`.

Отзыв записи через `revoke-write` прекращает приём старого общего приглашения и увеличивает его поколение. Старые ссылки и коды читают запись без выдачи нового доступа. Полный отзыв удаляет адрес чтения и приглашение вместе. Версия сервера до этих маршрутов продолжит обслуживать старые ссылки и действующие персональные ключи. Новые ссылки с `/join/` и их короткие коды требуют обновлённого клиента и сервера. Прочитать ещё действующую запись при откате можно по полной ссылке с исходным фрагментом `#v1/<id>/<secret>`.

### Отзыв доступа к сохранённой передаче

После смены ключа идентификатор управления остаётся прежним. Для GET записи, ссылки, QR и регистрации короткого кода браузер использует новый адрес чтения. Старая запись и короткий код возвращают 404. Действующие полные ссылки без смены ключа сохраняют прежний формат.

- GET настроек с личным Bearer возвращает `locator` и, после смены, личную зашифрованную обёртку `recovery`. Владелец также получает `ownerKey` и открытые ключи участников при наличии.
- POST настроек `member-key` записывает публичный ключ браузера из поля `key`. POST `claim` может передать этот ключ в той же операции, что и расход приглашения. После смены адреса запросы приглашения и входа передают текущий `locator`. Ссылка участника после смены включает идентификатор управления после `/group/` во фрагменте.
- Резерв записи принимает необязательный текущий `locator`, который проверяется и при фиксации. Для смены только владелец может передать `rotation` с новым `locator`, исключаемым `member` и массивом `recovery`. У каждого оставшегося участника и владельца есть ровно одна запись `{member, wrapper}`. Идентификатор владельца в этом массиве равен `owner`. Размер одной обёртки ограничен 4096 байтами.
- PUT за один шаг сохраняет новый шифротекст, адрес, обёртки, отзыв и аннулирование неиспользованных приглашений. PUT и GET возвращают версию содержимого отдельно (`contentVersion` в JSON и `X-Hop-Content-Version` при чтении), когда она отличается от версии фиксации. Смена доступа сама по себе не считается новой отправкой.

Откат приложения к сборке до смены ключей допустим для каталога, в котором ещё не выполняли смену. Сборка без поддержки этого протокола не должна обслуживать каталог со сменёнными адресами. Восстановление старого снимка также возвращает состояние разрешений на момент снимка. Для такого каталога сохраняется совместимая сборка или исправление накатывается вперёд.
