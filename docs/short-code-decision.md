# Решение по короткому коду · HOP-008

**Владелец выбрал локальную схему с одним сервером.** Доступ по коду включается владельцем передачи. При совместной утечке базы и закрытого ключа возможен офлайн-перебор. Условия для выбранной схемы описаны в [ADR 004](../ADR/004-single-server-short-code.md) и [контракте API](short-code-api.md). Ниже записаны сравнение и критерии исследования независимых контуров.

## Сравнение кандидатов

| Подход | Результат для hop |
| --- | --- |
| OPAQUE на одном сервере | Сервер штатно не получает пароль, но с секретами и базой можно проверять догадки офлайн. Протокол использует отдельный идентификатор записи. Оба вопроса остаются для восьмисимвольного входа. [RFC 9807, §10.7 и §10.11](https://www.rfc-editor.org/rfc/rfc9807.html) |
| TOPPSS или пороговая OPRF | Разделение секрета между независимыми контурами подходит для защиты при захвате одного из них. В модели TOPPSS получатель помнит пароль и идентификатор сохранённой записи. Анонимный поиск этой записи по одному коду требует отдельного механизма и анализа. [TOPPSS](https://eprint.iacr.org/2017/363) · [Формальная модель, §3.4](https://escholarship.org/uc/item/904296qr) |
| Защищённое восстановление по модели SVR3 | Signal ограничивает попытки по идентификатору аутентифицированного клиента. У нового получателя hop есть только код. Для переноса схемы нужны другая адресация, проверяемая независимость контуров и защита счётчика от отката. [Signal SVR3, §2.2 и §3](https://www.usenix.org/system/files/osdi24-connell.pdf) |
| Две детерминированные слепые RSA-подписи | Проверили механику поиска, захват одного ключа, ротацию и лимит. Для коротких входов скрытие кода зависит от честно созданного ключа подписанта. Два процесса на одной машине не дают независимости. Такой эксперимент нельзя принимать за выбранный протокол. [RFC 9474, §7.3](https://www.rfc-editor.org/rfc/rfc9474.html#section-7.3) |

## Анонимная адресация

Основной кандидат для дальнейшего сравнения использует все восемь символов как вход проверенного порогового вычисления. Клиент получает результат только с участием нужных контуров и выводит из него двумя раздельными функциями адрес зашифрованной записи и ключ к ней. Адрес индексирует зашифрованную запись с доступом к содержимому. Хранилище не получает код, ключ или публичный хеш кода. Браузер может открыть ту же передачу с сильным секретом из полной ссылки без вычисления короткого кода.

Это проект адресации для проверки, который пока не определяет криптографический протокол или внешние контракты. При захвате одного контура независимый второй контур должен ограничивать число выданных вычислений. До вычисления второй контур не знает конкретную передачу, а после вычисления атакующий уже может сохранить результат. Лимит только на чтение найденной записи этого не предотвращает. Разделение кода на открытый номер передачи и секрет позволяет считать попытки на передачу, но каждый открытый символ алфавита из 32 знаков сокращает пространство секрета в 32 раза. Публичный индекс вида `hash(code)` позволил бы проверять догадки по украденной базе без участия контуров.

Нужно определить, как выбрать активную версию вычисления и обработать совпадение коротких кодов у одновременно живых передач. Поиск по нескольким версиям расходует дополнительные вычисления. Чем дольше сохраняются старые ключи, тем дольше действуют накопленные ответы. Удаление старого ключа нельзя считать защитой, если атакующий сохранил нужный ответ или ключи заранее. Контур хранения и каждый участник восстановления должны иметь независимое управление секретами, счётчиками и восстановлением после сбоя.

## Численные критерии для выбора

При равномерных восьми символах из алфавита 32 пространство вариантов равно `2^40`. Если у атакующего есть `q` проверенных разных догадок для одной пары ключей, вероятность угадать конкретный случайный код равна `q / 2^40`. Для `N` кодов, к которым применимы эти догадки, верхняя граница составляет `min(1, N × q / 2^40)`. В `N` входят и коды удалённых передач, если атакующий скопировал записи и риск для них всё ещё считается. В `q` входят ответы, накопленные до публикации записей. Для нескольких пар складываются оценки по парам. Это оценка угадывания под указанными допущениями. Она не включает утечки из URL, клиента или протокола.

Для сравнения кандидатов предлагаем сценарный ориентир: риск хотя бы одного угадывания не выше `0,01%` на период пары ключей. При `N = 1 000` это даёт до 109 951 проверенной догадки за период. При `N = 10 000` остаётся до 10 995. Сохранённый лимит на все ответы честного контура можно использовать как консервативную верхнюю границу `q`. В неё тогда попадает и штатная выдача, что делает связь безопасности и доступности явной. Ориентир не утверждён владельцем и нужен для сравнения. Реальное `N`, период, допустимый риск и профиль трафика должны быть обоснованы перед выпуском.

Для проверки доступности предлагаем принимать не менее 99 из 100 честных открытий в каждом из профилей: обычный трафик, атака с одного источника и атака с нескольких источников в пределах измеренного профиля раннего запуска. Размер распределённой нагрузки и задержку нужно зафиксировать отдельно перед нагрузочной проверкой. Уже пройденный отрицательный контроль: при 40 догадках с десяти источников и 10 честных открытиях общий лимит позволил открыть только 4 передачи. Полная ссылка открылась после исчерпания этого лимита. Проверка подтверждает конфликт доступности у прототипа и не задаёт производственный лимит.

## Условия, рассмотренные для варианта с независимыми серверами

1. Выбрать реализацию проверенного протокола с описанным поиском и форматом записи. Показать, что при краже одной базы или базы и одной доли нельзя проверять новые догадки без оставшегося контура. Совместный захват оценить отдельно. Механика теста не заменяет независимую проверку протокола.
2. Измерить выдачу атакующему и долю честных открытий при одном и множестве источников. Проверить исчерпание лимитов, перезапуск, откат состояния, смену ключей и перенос накопленных ответов. В обоих маршрутах проверить отсутствие утечки кода и ключей в логах и индексах.
3. Пройти получение в свежем браузере по восьми символам без состояния отправителя. Проверить неверный код, неоднозначность записи, совместимость живых записей при ротации, отказ одного контура и открытие полной ссылки при недоступном коротком коде.
4. Подтвердить независимость контуров и согласовать компромисс доступности. Если публичный анонимный маршрут не проходит выбранный профиль, вынести конкретное изменение требований на решение владельца. Работа над полной ссылкой и хранением может продолжаться до этого решения.

Эти условия относятся к варианту с независимыми серверами. Для выбранной схемы проверка HOP-015 измерила бюджет и отказ. Числа записаны в контракте API.
