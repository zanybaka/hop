# Короткий код в API v1

Основание решения: [ADR 004](../ADR/004-single-server-short-code.md). Это дополнительный путь к сохранённой публикации по желанию её владельца. Сервер продолжает обслуживать полные ссылки и QR через API публикации v1. Старые ссылки и каталоги данных читаются как раньше.

| Запрос под `/api/v1/short-code/` | Назначение |
| --- | --- |
| `GET keys` | Возвращает текущий и доступный предыдущий ключи, каждый как `{epoch,key}`. `key` есть публичный RSA JWK |
| `POST evaluate` | Принимает `{epoch,blinded}` и возвращает `{signed}`. Оба значения RSA размером 384 байта, запись hex |
| `POST :id` | Принимает `{epoch,lookup,wrapper}` с полномочием владельца из API публикации. Возвращает 201 для новой записи и повтора того же адреса и периода |
| `GET :lookup` | Возвращает `{wrapper}` для живой публикации или `{wrapper,kind:"pair"}` для активного приглашения в пару |

`id` и `lookup` различаются по назначению, каждый занимает 32 байта в hex. Публикация допускает один код с успешной регистрацией. Существующий код для другой публикации даёт 409 `conflict`, клиент генерирует другой и повторяет запрос. Другой адрес для той же публикации даёт 409 `registered`. Ошибочный ввод даёт 400, отсутствие записи и истечение дают 404. Смена режима записи и приглашения участников используют прежний контракт. Короткий код самостоятельно даёт доступ только на чтение.

Клиент регистрирует ручное приглашение через `POST /api/v1/pairing/code` с `{epoch,lookup,wrapper}` и полномочием владельца приглашения. Сервис принимает один код на приглашение и проверяет совпадения с индексом сохранённых передач. Клиент узнаёт назначение кода из `kind`. Для пары обёртка содержит идентификатор приглашения и секрет сигнализации. После расшифрования клиент запрашивает обычный вход в пару. [Жизненный цикл приглашения](pairing.md).

Браузер генерирует код из алфавита `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`. Старший бит первого символа передаёт чётность текущего периода по UTC. Остаётся 39 случайных бит на ключ. Код не передаётся в HTTP. Браузер отправляет скрытый запрос к выделенному ключу RSA 3072, проверяет ответ как RSA-PSS SHA-384 с нулевой солью и выводит HKDF-SHA-384 64 байта для индекса и ключа обёртки. AES-GCM защищает 32 байта идентификатора и 32 байта ключа содержимого, привязывая их к индексу. Формат `wrapper` в hex содержит 12 байт IV и 80 байт шифротекста с тегом. Примитив слепой подписи описывает [RFC 9474](https://www.rfc-editor.org/rfc/rfc9474.html). Безопасность короткого входа предполагает честную генерацию ключа и подлинный код клиента. Спецификация RFC не проверяет весь протокол Hop.

Сервис меняет ключ ежедневно по UTC, сохраняет предыдущий ключ и открывает с ним ещё живые передачи. Истечение публикации проверяется по действующему сроку, чтение обёртки само по себе его не продлевает. На диске предел для записи кода равен абсолютному сроку публикации или окончанию второго периода ключа, что наступит первым. Фоновая очистка убирает закончившиеся периоды и записи. Копии, журналы SQLite и резервные копии могут удерживать старые данные.

Живой сервер ограничивает выдачу подписей по адресу соединения и суммарно. Рабочие значения для локальной проверки составляют 30 и 1800 запросов за минуту соответственно. Счётчики сохраняются после перезапуска, исходный адрес заменяется серверным HMAC. Вычисление принимает JSON и отклоняет запросы браузера с признаком чужого сайта. При превышении сервер отвечает 429 с Retry-After 60 секунд. Пограничные запросы могут использовать бюджеты двух соседних минут. Схему получения адреса за доверенным прокси и лимиты для реального трафика проверяет HOP-015. По умолчанию приложение использует адрес TCP-соединения. При HOP_TRUST_LOOPBACK_PROXY=1 сервер слушает только loopback и требует один допустимый IP в X-Hop-Client-IP. Прокси обязан перезаписывать этот заголовок адресом из доверенной цепочки.

Сервис хранит индекс и счётчики в `short-code.sqlite`, ключевой материал в отдельном файле `short-code-keys.sqlite` с доступом владельца процесса. Оба файла принадлежат одной машине. Их совместная утечка позволяет проверять догадки без HTTP. Потеря файла ключей может лишить открывания по созданным кодам. Полная ссылка и QR открывают данные через API публикаций. Откат к версии до коротких кодов сохраняет читаемость полных ссылок и не обслуживает коды до возврата новой версии с теми же файлами состояния.
