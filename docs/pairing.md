# Локальная модель приглашения в пару

`createPairing({ now, offerLifetime, maxOffers })` в `src/pairing.mjs` хранит в памяти приглашения для подтверждения с обеих сторон. Срок по умолчанию пять минут, предельное число живых записей 1024. При запросе модуль удаляет истёкшие записи. Каждое приглашение удерживает один слот до исходного срока, в том числе после отклонения, чтобы обе стороны могли забрать результат.

1. `offer()` выдаёт `invitation`, отдельный `owner` и `expiresAt`. Для QR предназначено `invitation`. `owner` остаётся у создателя.
2. `join(invitation)` сжигает приглашение и возвращает отдельный `recipient` с тем же сроком. Повторный вход по приглашению получает `missing`.
3. `status(owner)` и `status(recipient)` возвращают `state`, `role`, `expiresAt`. `decide(owner, 'approved' | 'declined')` принимает решение после входа получателя. `cancel(owner)` завершает ожидание до подтверждения.

Все три значения доступа случайные и независимые. В памяти модуль хранит их хеши. Токены владельца и получателя дают доступ только к своей записи. Просмотр статуса, вход и решение не продлевают срок. `PairingError.code` различает `invalid`, `missing`, `full`, `conflict` и `forbidden`. Истёкшие токены возвращают `missing`.

Модуль хранит состояние приглашения без текста и файлов. HTTP-сервис ограничивает создание приглашения по адресу и суммарно: при превышении ответ 429 с `Retry-After`. Само хранилище по-прежнему держит не больше 1024 живых приглашений до исходного срока. Состояние теряется после перезапуска. Транспорт, привязка сигнализации к обоим токенам, обнаружение устройств, обмен ключами и передача содержимого относятся к следующим задачам. Проверка: `node --test test/pairing.test.mjs`.

После подтверждения `writeSignal(token, { type, sdp })` принимает один `offer` от владельца и один `answer` от получателя. Ответ допускается после предложения. Каждый сигнал содержит только `type` и непустую строку `sdp` до 65 536 байт UTF-8. Точный повтор запроса допустим. Заменить уже записанное значение нельзя. `readSignal(token)` возвращает сигнал другой стороны или `null`. Чтение и запись используют исходный срок пары. Описание соединения может содержать сетевые адреса, поэтому транспорт не должен включать SDP в журналы. SDP используется только для согласования соединения. Клиенты не передают в нём содержимое или ключи передачи.

## Локальная интеграция

Сервер принимает запросы в `/api/v1/pairing`. `POST /offers` создаёт приглашение, `POST /joins` принимает его в JSON. `GET /status`, `POST /decision`, `POST /cancel`, `GET /signal` и `POST /signal` требуют Bearer соответствующей стороны. Сигналы разрешены после подтверждения. Обе стороны видят только сигнал собеседника. Ошибка связанного запроса возвращается как 400, 403, 404, 409, 429 или 507. Создание приглашения сверх предела даёт 429 и `Retry-After`. Вход по уже выданному приглашению этим пределом не закрывается.

Клиент генерирует отдельный случайный 32-байтовый секрет и помещает его вместе с приглашением во фрагмент ссылки. Он передаёт серверу только приглашение. Ключ для SDP выводится через HKDF-SHA-256 с идентификатором приглашения в соли. AES-GCM связывает SDP с приглашением и типом сигнала. Полезная нагрузка идёт по WebRTC в зашифрованных конвертах HOPG. Клиент не отправляет её через HTTP-сигнализацию.

Версия использует прямой WebRTC без внешних ICE-сервисов. Проверка на двух контекстах Chromium прошла для приглашения, отмены, отклонения, подтверждения, обмена в обе стороны, конфликта черновика и сохранения по ссылке после разрыва. При закрытии второго контекста оставшийся автоматически сохранил последнюю успешно переданную версию. Неотправленный черновик остался в редакторе и отсутствовал по ссылке. При отказе хранилища можно повторить сохранение вручную. В WebKit обмен SDP завершился, но прямой канал не открылся до таймаута. На физических устройствах и в разных сетях этот контракт еще не проверяли. Автообнаружение относится к HOP-010. После разрыва браузер сохраняет состояние по общему адресу продолжения. Возобновление прямого канала и общего режима записи отслеживается в HOP-011 и HOP-012.

Кадр передаваемой версии содержит девять открытых байтов внутри прямого канала: восьмибайтовый счётчик в сетевом порядке и один байт роли, где 1 обозначает создателя. Далее идёт HOPG. AES-GCM привязывает счётчик и роль через дополнительные данные, поэтому изменённый заголовок не проходит расшифрование. Клиент увеличивает наибольший принятый счётчик перед отправкой. При равных счётчиках выбирается версия создателя. Проигравший черновик остаётся в редакторе. В Chromium проверка с одновременными отправками подтвердила, что после разрыва открывается выбранная версия, а отдельный локальный черновик не публикуется.

Клиенты после установления прямого канала получают одинаковые адрес и ключ чтения. HKDF использует секрет приглашения и соль SHA-256 от UTF-8 JSON массива с идентификатором приглашения, SDP offer и SDP answer в этом порядке. Строки назначения `hop/continuation/v1/address`, `hop/continuation/v1/content` и `hop/continuation/v1/write` разделяют адрес, ключ чтения и разрешение записи участника. Ключ владельца генерируется отдельно и остаётся в его браузере. Создатель сохраняет пустую запись по общему адресу, выдаёт разрешение участнику и включает режим обмена. Пока прямой канал работает, текст и файлы идут по WebRTC.

После разрыва оставшаяся сторона сохраняет выбранное последнее состояние и продолжает запись с этой же ссылкой по HTTP. Новый браузер с обычной ссылкой получает чтение. Браузеры пары восстанавливают роль из локального хранилища. При неудачной подготовке доступна попытка сохранить снимок для чтения. Неотправленный черновик остаётся в редакторе. В Chromium проверено закрытие каждой стороны, отправка ответа после закрытия создателя и чтение ответа в вернувшемся браузере создателя. Повторное создание прямого канала пока требует нового QR-приглашения.

## Ручное подключение

При создании приглашения браузер показывает QR и автоматически пытается создать код из восьми символов. Второе устройство вводит код в поле на главной и ждёт решения владельца. Оба способа используют одно приглашение и один запрос на подтверждение. Первый запрос погашает оба способа входа. При закрытии окна владельцем или истечении срока приглашение становится недоступно.

Браузер использует действующий механизм слепой подписи и шифрует идентификатор приглашения и секрет сигнализации. Сервер хранит адрес зашифрованной записи и саму обёртку в памяти до погашения. Для создания записи владелец предъявляет право управления приглашением. Ввод в существующем поле использует один запрос к механизму проверки кода. Если создать код не удалось, владелец может использовать QR или полную ссылку приглашения.

## Права после подключения

Владелец переключает чтение или обмен в редакторе. Открытая вкладка получателя проверяет режим каждые 1,5 секунды. Получатель может вернуться к своему черновику в той же вкладке, когда владелец снова разрешит обмен. После перезагрузки права открываются из настроек по ссылке продолжения.

Перед отправкой браузер получателя проверяет разрешение записи. Браузер владельца повторяет проверку перед применением входящей версии. Если право записи закрыто, получатель получает кадр отказа с типом 4. Клиент прежней версии закрывает прямой канал при получении неизвестного кадра. Если сервер недоступен, прямой канал позволяет владельцу отправить данные, а запись получателя ждёт проверки прав. После разрыва сервер применяет сохранённые ограничения записи по той же ссылке.

Перед включением чтения владелец сохраняет зашифрованную копию последней переданной версии. В этом режиме владелец сохраняет новые версии после подтверждения прямой доставки, чтобы получатель мог открыть их по ссылке после ухода владельца. Если сохранение не прошло, владелец видит отдельное сообщение. В режиме обмена снимок сохраняется после разрыва.
